# Doc Gardening — 文档巡检与修复

对项目的文档目录与 AI 入口文件（CLAUDE.md / AGENTS.md）做系统性健康检查：找出断链、过时引用、互相矛盾的真源文档，输出分类报告并自动修复可修复的问题。

## 为什么这很重要

CLAUDE.md / AGENTS.md 和架构文档是 **AI Agent 进入仓库的第一入口**。如果这些文件引用了不存在的路径或包含过时信息，Agent 的所有后续决策都建立在错误上下文之上——所以它们的不一致是**最高优先级**问题，高于普通文档的陈旧。

## 可配置项

- **权威文档**：默认 `CLAUDE.md` 与 `docs/architecture.md`（按项目替换）
- **源码目录**：默认 `src/`、`packages/`（按项目替换，多仓项目逐仓配置）
- **报告输出**：`docs/reviews/doc-gardening-YYYY-MM-DD.md`
- **豁免目录**：决策记录、历史分析类文档（天然稳定，不算陈旧）

## 执行流程

### Phase 0: 准备

记录当前日期（报告文件名用）；确保报告目录存在；初始化三个分类：`needs_fix`（❌）、`needs_review`（⚠️）、`ok`（✅）。

### Phase 1: AI 入口文件的引用检查（最高优先级）

扫描 CLAUDE.md / AGENTS.md 中的：

1. `@path` 引用、`repos/...` / `packages/...` 引用——检查目标是否存在
2. 反引号中的文件/目录路径——检查是否存在
3. 代码块中的命令（构建/测试命令）——标记 ⚠️ 需人工确认是否仍有效

分类：路径不存在 → ❌ needs_fix；命令疑似过时 → ⚠️ needs_review；存在 → ✅ ok。

### Phase 2: 权威文档之间的一致性（最高优先级）

逐项对比 CLAUDE.md 与架构文档：

1. 模块/包清单是否一致
2. 依赖顺序描述是否一致
3. 目录结构描述是否矛盾
4. 版本号是否一致

任何不一致 → ❌ needs_fix——**Agent 会困惑该信任哪个文件**。

### Phase 3: 文档间的路径引用检查

遍历文档目录所有 .md：

1. Markdown 链接 `[text](path)` 的相对路径
2. `@path` 前缀引用
3. 反引号中疑似路径的字符串

分类：路径不存在 → ❌；含动态模式（`<`、`*`、`{`）→ 跳过；存在 → ✅。

### Phase 4: 函数名/接口名引用检查

1. 提取代码块外、反引号内的标识符（PascalCase/camelCase，长度 > 3）
2. 在源码目录搜索是否存在定义
3. 每个文档最多查 10 个（控制耗时），优先高频的

分类：代码中找不到 → ⚠️ needs_review（可能已重命名/删除）；存在 → ✅。

> 不标 ❌：反引号中的名称可能是概念描述而非精确代码引用，需人工判断。

### Phase 5: 陈旧文档检查

每个文档用 `git log -1 --format=%ci -- <path>` 取最后修改时间（**不用 mtime——clone 后会重置**）。超过 30 天：豁免目录（决策记录/历史分析）→ ✅；其他 → ⚠️ needs_review。

### Phase 6: 生成报告

输出到报告文件：概要（❌/⚠️/✅ 计数）→ ❌ 分「权威文档不一致」「断链引用」两类表格 → ⚠️ 分「疑似过时 API」「陈旧文档」两类表格 → ✅ 只给计数不逐条列。

### Phase 7: 自动修复（仅 ❌ 项）

1. **断链引用**：能推断出正确路径（如文件被重命名）→ 直接改引用
2. **权威文档不一致**：以代码现状为准，修改文档使其一致
3. 修复后在报告标注「已自动修复」

**不自动修复**：⚠️ 项（需人工判断）、需要删除整段内容的情况（风险太大）。

### Phase 8: 总结

向用户报告：报告文件位置、❌ 修复情况、⚠️ 重点关注项、是否建议提 commit（有自动修复改动时）。

## 红旗（说明这个仓库需要立即跑一次 doc-gardening）

- AI 入口文件引用了不存在的路径
- CLAUDE.md 与架构文档对同一事实的描述互相矛盾
- 大量文档超过 90 天未更新且不在豁免目录
