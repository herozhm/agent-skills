# style-priority-analysis

## 触发条件

- 用户说「分析 !important」「帮我看看这些 important 能不能去」「检查 important 是否必要」
- 打开了一个 .vue / 样式文件想清理 !important
- 想批量评估样式债务能不能还

## 分析覆盖的三层来源

1. **文件内部 CSS 规则**——同文件 style 块内的竞争规则
2. **组件库 CSS**——搜索组件库 dist 目录,找目标 class 的规则
3. **组件库 JS 内联样式**——搜索组件库 dist JS,检测动态 style 绑定

**特异性计算**:scoped 样式会给选择器加属性标记(如 Vue 的 [data-v-xxx]),脚本自动计算编译后的真实特异性并显示差异。

**库映射**(通过选择器内部 class 名前缀推断):在脚本顶部 LIB_PREFIX_MAP 配置——按你的技术栈填「类名前缀 → 组件库位置」。

## 工作流

### Step 1: 确定目标文件

用户指定或取当前打开的文件;无法确定时询问。

### Step 2: 运行分析脚本

```bash
pnpm tsx skills/style-priority-analysis/scripts/analyze.ts <文件路径>
```

脚本输出三档结论:

- ✗ !important 必须保留——组件库有内联样式竞争,或存在更高特异性 CSS 规则
- ✓ 可安全去掉——编译后特异性已 ≥ 所有已知竞争规则,!important 冗余
- ? 需人工确认——找不到组件库 dist,无法完成静态分析

### Step 3: 解读结果,给出建议

**✗ 必须保留(组件库内联样式)**:该属性由组件通过 JS 动态绑定 style,内联样式的优先级高于任何 class 规则,只有 !important 才能覆盖。如果将来组件库提供对应的 prop 或 CSS 变量,可改用那种方式。

**✗ 必须保留(CSS 竞争规则更高)**:去掉后会被更高特异性规则覆盖。建议先定位来源后从源头修改,而非堆 !important。

**✓ 可安全去掉**:编译后特异性已足够,直接删。删除后在 DevTools 确认视觉不变。

**? 需人工确认**:无法静态分析时——在浏览器 DevTools 中去掉 !important,观察是否有其他规则生效。若没有 → 直接删;若有 → 定位来源后处理。

### Step 4: 输出汇总报告

向用户呈现精简结论(不重复脚本原文):总数、✗ 必须保留(逐条原因)、✓ 可安全去掉(逐条)、? 需人工确认。

## 已知局限(诚实声明)

- **内联样式检测是启发式的**:通过 style: 上下文加类名共存判断,可能误报——误报方向是「保留」而非「误删」,更安全
- **无法感知运行时条件**:动态绑定的 class、计算属性生成的样式,需要 DevTools 验证
- **全局 CSS / 父组件样式**未参与搜索(范围太广),有疑虑用 DevTools 二次确认
- **不要自动修改文件**:分析只给建议,修改须用户确认后执行
